# GenericParser

header-only библиотека комбинаторных парсеров для C++20. Предназначена для создания типобезопасных, расширяемых и эффективных синтаксических анализаторов с минимальными накладными расходами.

Библиотека вдохновлена Boost Spirit x3 https://github.com/boostorg/spirit.git

Основной мотивацие для написания библиотеки было изучение шаблонов и работы с типами через концепты в рамках С++20. Также было интересно разобраться в constexpr/consteval семантике.

## Архитектура библиотеки

Библиотека построена на паттерне **Parser Combinators**. Сложные правила грамматики собираются из простых, как конструктор, с сохранением полной типобезопасности на этапе компиляции.

Поток данных при парсинге выглядит следующим образом:
1. **Сканнеры (Scanners)**: Низкоуровневые предикаты, проверяющие отдельные символы или последовательности (аналоги `std::isalpha`, `std::isdigit`).
2. **Базовые парсеры (Base Parsers)**: Обертки над сканнерами, которые управляют состоянием потока (итераторами) и возвращают конкретные типы данных (например, `int`, `std::string`).
3. **Комбинаторы (Combinators)**: Перегруженные операторы (`>>`, `*`, `%`, `|`, `!`), которые объединяют парсеры в сложные структуры, автоматически формируя типы возвращаемых значений (`std::tuple`, `std::vector`, `std::variant`).
4. **Семантические действия (Semantic Actions)**: Лямбда-выражения, прикрепляемые к парсеру через оператор `[]`. Они перехватывают контекст (`ctx`) и преобразуют "сырой" результат парсинга 
	в нужную бизнес-логику (AST, вычисления, маппинг). Все парсеры имеют доступ к контексту (ctx) для получения результата парсинга дочерних парсеров. Явно получить этот контекст можно только 
	через ParserWithAction

## Подробный каталог возможностей

### 1. Богатый набор базовых парсеров (доступны через `namespace aliases`)
* **Числовые:** `int_`, `uint_`, `long_int_`, `long_uint_`, `float_`, `double_`, `long_double_`. Корректно обрабатывают знаки, ведущие нули и экспоненциальную запись.
* **Строковые (до разделителя):** `str_alpha`, `str_alnum`, `str_digit`, `str_xdigit`, `str_space`, `str_print` и др. (аналоги функций из `<cctype>`, применяемые к последовательностям).
* **Символьные:** `char_alpha`, `char_digit`, `char_any`, `char_space` и др. (возвращают одиночный символ).
* **Литералы:** `ParserLiteralWithContext{"text"}` для точного совпадения строк или символов.

### 2. Комбинаторы
Библиотека перегружает операторы для интуитивного описания грамматики:
 **Repeat**
	Парсеры, повторяющий парсинг дочернего парсера указаное кол-во раз. 
	Синтаксис:
		*parser - 0 или более срабатываний Parser
		+parser - 1 или более срабатываний Parser
		n*parser - ровно n срабатываний Parser
	Примеры:
		parser_ints = *int_{}"  - распарсит, например, "1 2 3 4 5" и вернет std::vector<int>{1,2,3,4,5}
	Возращаемый тип - std::vector
	
 **List**
	Тот же Repeate, но с разделителем. Разделителем может выступать любой другой парсер 
	Синтаксис:
		parser % <delimiter_parser> - 0 или более срабатываний Parser, инпут которого должен быть разделем тем, что прожует delimiter_parser
	Пример:
		parser_list_ints = int_{} % ","  - распарсит, например, 1,2,3,4,5 и вернет std::vector<int>{1,2,3,4,5}
		parser_list_ints = int_{} % "[a]"  - распарсит, например, 1 [a] 2 [a] 3 [a] 4 [a] 5 и вернет std::vector<int>{1,2,3,4,5}
	Разделитель всегда помечен как omited, т.е. игнорируется. 
	Возращаемый тип - std::vector
	
 **Alternative:**
	Парсер с выбором. Буквально "либо A либо B либо ..."
	Синтаксис:
		parser_a | parser_b | ...
	Примеры
		parser_int_or_literal = int_{} | str_alnum - спарсит либо int либо любую alphanumerical строку. Если не найдет ни одного из вариантов - вернет false
	
	Возращаемый тип - std::variant
	
 **PredicateNot**
	Парсер, который не возвращает атрибут, но возвращает true в случае, если вложенный парсер найдет вхождение строки
	
	Пример:
		parser_not_integer = !int_{}
		для строки "a" вернет true, для строки "123" вернет false. Используется по большей части в сложных выражениях при проверке условий
		Пример реального использования из JsonTests.h :
			parser_string = ("\"" >> (*(!ParserLiteralWithContext{ "\"" } >> ("\\\"" | ParserLiteralWithContext{ "\\\\" } | aliases::char_any))) >> "\"")[action_on_str];
			смотрит что строка обернута в кавычки, а сами кавычки экранированы. Также защищает от ложных срабатываний на экранированный слеш. Также проверяет экранированные кавычки внутри самой строки(способ записи кавычек внутри json строки)
			Как можно видеть, *(!ParserLiteralWithContext{ "\"" } >> ("\\\"" | ParserLiteralWithContext{ "\\\\" } | aliases::char_any)) просто "проходит" валидные символы, а потом через action_on_str преобразует пройденную подстроку в std::string

		Возвращаемый тип отсутствует. 
		
 **Sequence**
	Парсер последовательного выполнения. Срабатывает (возвращает true) если все перечисленные дочерние парсеры срабатывают
	Возвращаемое значение - std::tuple<types...>, types - типы дочерних парсеров
	
	Пример:
		"[" >> int % ',' >> "]" - парсит строки вида [1,2,3,4,5,6] и возвращает std::tuple<std::vector<int>>, т.к. литераты считаются omited парсерами (атрибут помечен как tag_attribute_unused, т.е. игнорируется в результате)
		("[" >> int % ',' >> "]") >> ("{" >> str_alpha{} >> "}") - спарсит [1,2,3,4,5,6]{"banana", "apple"} и вернет std::tuple<std::vector<int>, std::vector<std::string>>

	Возвращаемый тип - std::tuple
	
 **ParserWithAction**
	Обертка над любым парсером, конвертирующая его результат через лямбды(другие callable на стадии разработки, почему-то, я не рассматривал)
	
	Синтаксис:
		parser_with_action = parser[action]
	Пример
	auto l_multiply = [](auto& ctx){return ctx.GetValue()*2;};
	auto parser_mult_int = int_{}[l_multiply];
	parser_mult_int для строки "123" вернет 246
	
	Впринципе, в лямбде можно описать любое доступное преобразование. Но ParserWithAction всегда должен возвращать значение! В обратном случае код просто отвалится через static_assert на этапе компиляции
	
 **Rule** 
	Впринципе, forward declaration для парсеров. Используется для рекурсивного парсинга. 
	
	Обратимся к примеру из JsonTests.h:
		RuleNew<class tag_value, SJsonValue> value;
		RuleNew<class tag_object, SJsonValue> object;
		RuleNew<class tag_array, SJsonValue> array;
		/* имплементация промежуточных парсеров строк/булей/чисел. Для примера не важно */
		auto parser_object = "{" >> (*((parser_string >> ":" >> value) % ",")) >> "}";
		auto parser_array = "[" >> (*(value % ",")) >> "]";
		auto parser_value = object | array | parser_null | parser_bool | parser_float | parser_int | parser_string;

		IMPLEMENT_RULE(object, parser_object[action_on_object]);
		IMPLEMENT_RULE(array, parser_array[action_on_array]);
		IMPLEMENT_RULE(value, parser_value[action_on_value]);
		
	SJsonValue - обычная структура.
	Сначала мы объявляем парсер - RuleNew<class tag_value, SJsonValue> value. tag нужен просто для того чтобы шаблоны не путались при инстанцировании. Подобная же фича есть в boost spirit. Далее, мы через комбинирование парсеров
	создаем некоторый парсер-обертку (parser_object, например). Далее через макрос IMPLEMENT_RULE(object, parser_object[action_on_object]) мы связываем продекларированный парсер с его "имплементацией". 
	ОБЪЯВЛЕННЫЙ ТИП ВОЗВРАЩАЕМОГО ЗНАЧЕНИЕ ОБЯЗАН СОВПАДАТЬ С ВОЗВРАЩАЕМЫМ ТИПОМ ИМПЛЕМЕНТАЦИИ!
	
	В результатет мы имеем парсер object, который ссылается на парсер value/array, которые в свою очередь ссылаются на сам object. Иначе эту шаблонную рекурсию, видимо, не разрешить.
	
	Тесты с json разных размеров отрабатывают(128kb - 5mb), на результат парсинга, впринципе, можно посмотреть в отладчике. 
	
	
Все описанные выше парсеры(кроме Rule), удобны для использования в том смысле, что пользователь не обязан знать их тип. Базовый парсинг регулярных грамматик становится довольно понятным.
